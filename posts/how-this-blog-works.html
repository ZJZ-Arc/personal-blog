这个博客是怎么搭起来的：零依赖三件套

目录结构、相对路径、深色模式、标签筛选和目录，全部拆开讲一遍。

2026年10月10日
阅读时长: — 分钟

这个站没有框架、没有 npm 依赖、没有构建步骤。整个「技术方案」就是浏览器原本就会的三样东西： HTML 负责内容，CSS 负责样子，JavaScript 负责那点交互。看懂这一篇，你就看懂了这个站的全部。

一、目录结构

personal-blog/
├── index.html          # 首页：自我介绍 + 标签筛选 + 文章列表
├── tags.html           # 所有标签的总览页
├── about.html          # 关于我
├── posts/              # 每篇文章一个 HTML 文件
│   ├── hello-world.html
│   └── how-this-blog-works.html
├── templates/
│   └── post.html       # 新文章模板
├── tools/
│   ├── new-post.mjs    # 一条命令生成新文章骨架
│   ├── check.mjs       # 发布前自检
│   └── set-domain.mjs  # 换站点地址时批量改绝对网址
├── assets/
│   ├── style.css       # 所有样式，颜色都是变量
│   ├── main.js         # 主题切换 + 标签筛选 + 目录 + 阅读时长
│   └── avatar.jpg      # 头像（换成自己的照片即可）
├── feed.xml            # RSS 订阅源
├── sitemap.xml         # 给搜索引擎的页面清单
├── robots.txt
├── .nojekyll           # 告诉 GitHub Pages：别用 Jekyll 处理我的文件
└── README.md

注意文章全部放在 posts/ 子目录里。这不是强迫症，而是为了「相对路径」能算得清楚。

二、相对路径：让同一份代码在本地和线上都能跑

所有链接都写成相对路径，不写 /assets/style.css 这种绝对路径： 

<!-- 首页在根目录 -->
<link rel="stylesheet" href="assets/style.css">

<!-- 文章在 posts/ 里，要往上退一层 -->
<link rel="stylesheet" href="../assets/style.css">

这么写有三个好处：双击本地文件就能预览；搬到 GitHub Pages 的项目仓库（网址是 用户名.github.io/仓库名/）不会 404；以后换域名也不用改任何一行代码。

但要注意区分两类地址：链接用相对路径，元信息必须写绝对网址。 canonical、og:url、RSS 里的 <link> 和 sitemap 都要求完整网址， 而项目站点的完整网址是带仓库名的——这个站就是 https://zjz-arc.github.io/personal-blog/。 换域名时用 node tools/set-domain.mjs 一次性改完，再靠自检脚本确认没有漏改。

三、三栏布局与深色模式

页面结构是「左侧导航 + 中间卡片 + 右侧目录」三栏，全部用 Flexbox 实现： 左侧栏和右侧栏用 position: sticky 跟着滚动，正文则装在一张卡片里。 颜色全部写成 CSS 变量，深色模式只是换一组变量值： 

:root {
  --body-background: #e8f1fb;
  --card-background: #fff;
  --card-text-color-main: #000;
  --sidebar-menu-color: #c2255c;
}

:root[data-theme="dark"] {
  --body-background: #1b2a3a;
  --card-background: #27394d;
  --card-text-color-main: rgba(255, 255, 255, 0.9);
  --sidebar-menu-color: #ff9ecb;
}

两个容易踩的坑我提前处理了：

  • 闪白屏。如果在 body 末尾才读 localStorage，页面会先用浅色画一遍再变深色。 解决方法是把一小段脚本放在 <head> 里、CSS 之前执行。
  • 记住用户的选择。手动切过就写进 localStorage； 没切过就跟随系统，并且系统主题变了也跟着变（matchMedia 监听）。

四、目录和阅读时长都是现算的

右侧的「目录」不是手写的。脚本扫描正文里的小标题，把 h2 当成一级、h3 当成二级， 生成嵌套的列表，顺便给每个标题补上 id： 

// 简化版：真正的实现见 assets/main.js
var headings = content.querySelectorAll("h2, h3");
headings.forEach(function (h) {
  if (!h.id) h.id = slugify(h.textContent);
  // 按层级塞进对应的 <ol>
});

「1. / 1.1 / 1.2」这种编号不是拼字符串拼出来的，而是 CSS 计数器 （counters(item, ".")）算出来的，所以层级再深也不会乱。 阅读时长同样是现算：中文按 400 字/分钟、英文按 200 词/分钟估一个值。

五、标签筛选：状态放在 URL 里

首页每个列表项上挂着它自己的标签：

<li class="post-item" data-tags="教程 前端"> ... </li>

点击标签时，JS 遍历所有 [data-tags]，不匹配的就设成 hidden， 同时把当前标签写进地址栏的查询串（?tag=教程）。为什么非要用 URL 存状态？

  1. 标签总览页可以直接链接过来，分享给别人也能直接看到筛选结果；
  2. 刷新和浏览器前进后退都不会丢状态；
  3. 整个筛选逻辑不需要服务器，纯前端就能完成。
小细节：筛选时用的是 history.replaceState 而不是 pushState。 否则用户点五次标签，就要按五次返回键才能离开这个站。

六、RSS 和 SEO

feed.xml 是一个手写的 RSS 2.0 文件，每发一篇文章加一个 <item>。 同时每个页面的 <head> 里都有 title、description、 canonical 和 Open Graph 标签，这是搜索引擎和社交平台判断「这个页面讲什么」的依据。

因为没有构建步骤，这些元信息是手写的——这正是零依赖方案要付的代价。 网站规模小的时候完全划算；等你有五十篇文章、每次发帖要改六个文件时， 就该考虑换成 Astro 或 Hexo 这类工具了。

为了对抗「手工维护容易漏」，项目里带了自检脚本 node tools/check.mjs： 它检查断链、标签计数、RSS 与 sitemap 是否和真实文章对齐。退出码在有问题时非 0， 所以既能本地跑，也能接进 CI。

七、发布到 GitHub Pages

思路只有四步，详细命令写在项目的 README 里：

  1. 在 GitHub 建一个仓库（想要 用户名.github.io 这样的网址，仓库名就得这么取）；
  2. 把本地文件 git push 上去；
  3. 仓库的 Settings → Pages 里把 Source 设为 main 分支的根目录；
  4. 等一两分钟，访问分给你的网址。

根目录那个 .nojekyll 空文件别删。GitHub Pages 默认会用 Jekyll 处理你的文件， 而 Jekyll 会忽略掉以下划线开头的文件、并可能改掉你的输出结果；放一个空文件就能关掉它。

八、什么时候该换方案

我把话说在前面：这套方案不是万能的。出现下面任一情况，就说明你该迁移了—— 这正是「知道原理」比「会用某个工具」值钱的地方，迁移时你清楚每一部分对应什么。

  • 每次发文章要手动改四个以上文件，而且你开始因此拖延写作；
  • 需要在文章里用复用组件、图片自动压缩、代码高亮；
  • 想要草稿、定时发布、多语言这些功能。

那时候就直接换 Astro——你现在写的内容一个字都不会浪费，它们本来就是 HTML。
